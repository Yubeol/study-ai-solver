# 2026-10-01 질의 흐름(질문 → 답변) + 페이지 넘는 코드 설계

## 무엇을 만들었나

### 1. 서버 메모리·속도 측정
임베딩 모델(BGE-M3)과 리랭커(bge-reranker-v2-m3)를 한 서버에 같이 올렸을 때 메모리와 질문당 시간을 쟀습니다. 메모리는 최대 약 4.7GB였고, 질문 하나에 임베딩 0.1초, 벡터 검색 0.4초, 리랭크 약 4초가 걸렸습니다. 리랭커 입력 길이(`RERANKER_MAX_LENGTH`)를 512로 줄여 봤지만 결과·속도가 1024와 같아서 1024를 그대로 둡니다.

### 2. "자료에서 확인 불가" 3구간 판단
검색 결과 1위의 리랭커 점수로 질문을 세 구간에 나눕니다. 0.03 미만은 LLM을 부르지 않고 바로 "자료에서 확인 불가", 0.03~0.15는 "회색 구간"(답은 하지만 "근거 확신 낮음" 표시), 0.15 이상은 그대로 답변합니다. 예전에는 0.15 하나로 잘라서 교재에 있는 내용(시계열 차분, 향상도)도 "없다"고 답하던 문제를 고쳤습니다.

### 3. 질의 API `POST /qa`
질문을 보내면 교재에서 근거 5개를 찾고, Gemini가 그 근거만으로 시험형 답변(핵심 답 → 설명 → 헷갈리는 개념)을 JSON으로 만듭니다. 답변이 인용한 근거 번호가 실제로 넘긴 근거 안에 있는지 코드로 검사하고, 근거에 답이 없으면 Gemini도 "확인 불가"라고 답하게 해 한 번 더 거릅니다. 모든 질문은 팀 테이블 `query_logs`에 기록됩니다.

### 4. 페이지를 넘는 R 코드 조사와 설계(코드 변경 없음)
교재 R 코드가 페이지 끝에서 잘려 다음 페이지로 이어지면 청크가 둘로 나뉘고, 뒷부분 출력 조각이 검색에서 빠지는 문제를 조사했습니다(3과목에서 확실한 경우 6건, 검색에서 빠진 조각 3건). 이어진 코드 블록만 예외로 한 청크로 합치는 설계를 문서(D-026)로 남겼고, 구현은 다음 작업 2번입니다.

### 5. 팀 공유 문서
`docs/team/`에 팀원도 쓸 수 있는 문서 두 개를 만들었습니다. PaddleOCR을 Windows + CPU에서 돌리는 설정(검증 완료)과 페이지를 넘는 코드 처리 방법(설계 초안)입니다. 교재 원문, 내 스키마 이름, `.env` 값은 넣지 않았습니다.

## 어떻게 돌아가나

**서버를 켤 때**: `backend/app/main.py`의 `lifespan`이 DB 커넥션 풀을 연 뒤 `backend/app/qa/service.py`의 `load_qa_models`를 부릅니다. 이 함수가 임베딩 모델과 리랭커를 메모리에 올리고 한 번씩 돌려 둡니다(약 1분). 처음 질문이 들어올 때 모델을 올리면 26초씩 기다려야 해서 미리 해 두는 것입니다. Gemini 연결 객체(`backend/app/llm/gemini.py`의 `GeminiClient`)와 판정기(`backend/app/judge`, 지금은 "없음")도 이때 준비합니다.

**질문이 들어오면** (`backend/app/api/qa.py`의 `ask` → `service.answer_question`):
1. 질문을 임베딩해 숫자 벡터로 바꾸고, `backend/app/retrieval/search.py`의 `search_theory`가 DB의 `v_searchable_theory`에서 가까운 청크 10개를 가져옵니다.
2. 1위 벡터 점수가 0.45 이상이면 `backend/app/retrieval/rerank.py`의 `rerank`가 질문과 청크를 함께 읽어 다시 점수를 매기고 상위 5개만 남깁니다.
3. `search.py`의 `is_answerable`이 벡터 1위·리랭커 1위 점수로 구간(reject / gray / answer)을 정합니다. reject면 여기서 "자료에서 확인 불가"로 끝납니다.
4. gray나 answer면 근거 5개를 `[1] 과목 / 쪽 / 제목 경로 + 본문(clean_text)` 형태로 묶어 Gemini에 보냅니다. 문장은 `backend/app/prompts/answer_system.txt`(규칙), `answer_user.txt`(근거·질문 배치), `answer_evidence_item.txt`(근거 1개 모양)에서, 응답 모양은 `answer_schema.json`에서 읽습니다. Gemini가 바쁘면(429/503) 2→4→8초 기다리며 다시 시도합니다.
5. 받은 JSON에서 `cited`(인용 번호) 중 1~5 밖인 번호와 본문 속 잘못된 `[번호]`를 지우고 기록합니다. Gemini가 `unanswerable=true`로 답하면 "자료에서 확인 불가"로 바꿉니다. gray 구간 답변이나 유효 인용이 없는 답변에는 `low_confidence=true`(근거 확신 낮음)를 붙입니다.
6. 응답의 근거 표시는 교재 원문(`raw_text`)으로 돌려줍니다. 마지막으로 `backend/app/repositories/query_logs.py`의 `insert_query_log`가 팀 테이블 `query_logs`에 질문, 넘긴 청크 id, 답변, 전체 시간, 토큰 수를 쓰고, 구간 판정·단계별 시간·인용 검사 결과는 `metadata`(JSON) 칸에 넣습니다. 컬럼은 추가하지 않았습니다.

**샘플 실행**: `backend/app/qa/sample_run.py`가 평가 질문 CSV에서 고른 id만 켜져 있는 서버의 `/qa`로 보내고, 결과를 `data/reports/answers/{시각}.json`과 `.md`(질문·판정·답변·인용 원문)로 저장합니다. Gemini 무료 한도 때문에 한 번에 12개까지만 돌립니다.

## 직접 확인하는 방법

1. 테스트: 저장소 루트에서
   ```powershell
   uv run pytest
   ```
   기대: `95 passed, 3 deselected`

2. 서버 켜기(모델 로딩 약 1분 기다리기):
   ```powershell
   cd backend
   uv run uvicorn app.main:app
   ```
   기대: 로그에 `Application startup complete.` 작업 관리자에서 python 메모리 약 4.6GB.

3. 브라우저에서 http://127.0.0.1:8000/docs → `POST /qa` → Try it out → 본문 `{"question": "장바구니 분석에서 lift가 1이면 무슨 뜻이야?"}` → Execute
   - 기대: `zone`이 `gray`, `status`가 `answered`, `low_confidence`가 `true`, `citations`에 339쪽 근거(`raw_text`는 교재 원문)
   - 자료에 없는 질문 `{"question": "CNN에서 풀링 레이어는 왜 넣는 거야?"}` → `zone`이 `reject`, `answer`가 "자료에서 확인 불가", 0.5초 안팎

4. 샘플 몇 개를 한 번에(서버를 켠 상태로 다른 창에서):
   ```powershell
   cd backend
   uv run python -m app.qa.sample_run --ids c06,c09,n08
   ```
   기대: 질문별 `zone/status`가 찍히고 `data/reports/answers/{시각}.md`가 생김. 오늘 결과는 `data/reports/answers/20261001-091851.md`(10문항).

5. DataGrip: `mingyu.query_logs`를 `created_at` 내림차순으로 보면 질문마다 1행. `metadata` 칸에 `zone`, `zone_reason`, `timings_ms`(embed/vector/rerank/llm/total), `cited`, `citation_check`가 있음.

6. 명령줄 검색에서 3구간 확인:
   ```powershell
   cd backend
   uv run python -m app.retrieval.search "시계열 평균이 계속 올라가면 뭘 해야 해?"
   ```
   기대: "판단: 회색 구간(근거 확신 낮음)(rerank_gray)" 같은 줄.

7. 문서: `docs/team/paddleocr-windows-cpu.md`, `docs/team/cross-page-code.md`(팀 공유용), `docs/DECISIONS.md`의 D-025(질의 흐름)·D-026(페이지 넘는 코드).

## 아직 안 되는 것
- 판정기(Jev)가 없습니다. 회색 구간은 판정 없이 답하고 "근거 확신 낮음"만 붙입니다(다음 세션 1-c). `.env`의 `JUDGE_PROVIDER`를 none 외 값으로 바꾸면 서버가 시작할 때 오류가 납니다.
- 답변이 근거와 맞는지 다시 확인하는 단계(verify), 답변을 `mingyu_app.solutions`에 자세히 저장하는 것은 아직 없습니다(`query_logs` 요약만).
- 답변까지 약 6~7초 걸리고 그중 리랭크가 약 4초입니다. 화면(프론트)이 없어 진행 표시도 없습니다.
- 페이지를 넘는 R 코드 합치기는 설계만 했고 청킹 코드는 그대로입니다(135·142·143쪽 출력 조각은 여전히 검색 제외).
- "확인 불가" 기준값(0.45 / 0.03 / 0.15)은 Claude가 만든 33문항 기준 잠정값이라 실제로 쓰면서 다시 맞춰야 합니다.
- 샘플 답변 품질: 헷갈리는 개념 문장에 근거 번호가 빠지거나(a01), 설명이 근거 문장을 어색하게 이어 붙이는 경우(c07)가 있어 프롬프트를 다듬을 여지가 있습니다.
