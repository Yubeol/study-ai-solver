# 2026-10-01 팀 비교 준비 — 답변 온도 고정, 객관식 풀이 규칙, 기출 자동 채점·비교

팀원 프로젝트와 같은 질문으로 결과를 비교하기 전에, 데이터와 상관없이 우리 점수를 깎거나 결과를 흔드는 원인 두 가지를 고쳤다. 재청킹·재임베딩·DB 구조 변경은 하지 않았다. (팀 비교 자체는 상대 쪽 데이터가 준비되지 않아 보류됐다.)

## 무엇을 만들었나

**1. 답변 온도 0 고정**
Gemini가 답을 만들 때의 무작위성(temperature)을 0.2에서 0으로 낮췄다. 전에는 같은 문제를 다시 돌리면 15문제 중 1~2문제의 결과가 바뀌어 수정 전후를 비교할 수 없었다. 이번에 두 번 돌렸을 때 고른 번호와 판정이 모두 같았다.

**2. 객관식 풀이 규칙 (답변 프롬프트 규칙 8)**
전에는 "적절하지 않은 것은?" 같은 문제에서 보기 하나라도 교재 근거에 없으면 문제 전체를 "자료에서 확인 불가"로 거절했다. 이제는 보기를 하나씩 근거와 대조한다. 근거와 정면으로 어긋나는 보기를 먼저 고르고, 그런 보기가 없을 때만 "근거에 없는 보기가 딱 하나"이면 그 보기를 고른다. 근거에 없는 보기가 둘 이상이면 찍지 않고 거절한다. 검색이 근거를 5개만 가져오기 때문에 보기가 우연히 검색에 안 걸렸을 수도 있어서다. 답은 "정답은 ③이다 [1]." 한 문장으로 쓰고, 설명은 보기마다 한 줄씩 판단과 근거 번호를 적는다.

**3. 기출 자동 채점과 실행 비교 리포트**
기출 확인 스크립트가 답에서 "정답은 ③"의 번호를 뽑아 정답 번호와 맞춰 보고 맞음/틀림을 자동으로 매긴다. 보기 기호가 ①, 3, (3) 중 어느 모양이어도 같은 번호로 본다. 거절했거나 번호를 못 뽑은 문제만 "검토 필요"로 남기고, 사람이 이유를 적어 수동으로 채점한다. 여러 번 실행한 결과와 수정 전 결과를 한 표로 비교하는 `compare` 명령도 추가했다.

**4. DB 출처 확인 (조회만)**
DB에 들어 있는 이론·표·코드·기출은 모두 text.zip(페이지 사진 전체 OCR)의 쪽별 txt에서 왔다. 팀원의 구조화 결과 JSON은 쓰지 않았다. 처리 이력(processing_runs)의 PARTIAL 3건은 교재를 처음 넣을 때의 기록이고, 원래 규칙대로라 정상이다. 지금 324쪽은 모두 임베딩까지 끝나 있다.

## 어떻게 돌아가나

질문이 `POST /qa`로 들어오면 `backend/app/qa/service.py`의 `answer_question`이 처리한다. 순서는 다음과 같다.

1. 교재에서 근거 5개를 검색한다.
2. "확인 불가" 3구간 판단을 한다. 이 부분은 이번에 바꾸지 않았다.
3. `_generate`가 Gemini에 답을 요청한다. 이때 쓰는 규칙은 `backend/app/prompts/answer_system.txt`(이번에 규칙 8 추가)와 `answer_schema.json`이고, 온도는 설정값 `ANSWER_TEMPERATURE`(`backend/app/core/config.py`, 기본 0)를 쓴다.
4. 돌아온 답은 `validate_citations`가 검사한다. 인용 번호가 범위 안에 있는지, 인용 없는 문장이 몇 개인지 센다. 이때 "③은 근거에서 확인되지 않는다." 같은 보기 줄은 인용이 없는 게 맞으므로 따로 센다(`count_unsupported_options`). 결과는 응답의 `llm.citation_check`와 DB `mingyu.query_logs.metadata`에 남는다.

기출 확인은 `backend/app/qa/mcq_run.py`가 맡는다. 단계마다 쓰는 파일과 함수는 다음과 같다.

1. `run`: 선택 파일 `data/eval/mcq_selection.json`의 15문제를 서버의 `/qa`로 하나씩 보낸다. 답이 오면 `extract_choice`로 번호를 뽑고, `auto_grade`로 자동 채점해 `data/reports/mcq/{시각}.json`과 `.md`에 저장한다.
2. `report`: 사람이 쓴 `{시각}.grades.json`(검토 필요 문제의 수동 채점)을 `final_grades`로 자동 채점 위에 덮어서 리포트를 다시 쓴다. 리포트 구성은 다음과 같다.
   - 맨 위: 과목별 정답률, 틀림 수는 따로 강조
   - 비교용 표: 문제 ID / 정답 / 고른 번호 / 판정 / 인용 쪽 / 시간
   - 문제별 답변 전문
3. `compare`: 여러 실행 결과와 기준선을 읽어 `compare-{시각}.md`를 만든다. 실행끼리 결과가 바뀐 문제와, 기준선과 다른 문제를 표시한다.

## 직접 확인하는 방법

1. 테스트: 저장소 루트에서 `uv run pytest` → `110 passed`
2. 온도 설정: `.env`에 `ANSWER_TEMPERATURE=0`이 있는지 본다. 서버를 켜고 `/docs`에서 `POST /qa`를 실행하면 같은 질문은 거의 같은 답이 나와야 한다.
3. 비교 리포트 열어 보기: `data/reports/mcq/compare-20261001-183624.md`
   - 기대 결과: 수정 전 9/15 → 이번 2회 모두 12/15(80%), 틀림 0
   - "실행 간 바뀐 문제: 없음"
4. 실행별 리포트: `data/reports/mcq/20261001-183237.md`
   - 맨 위에 과목별 정답률과 비교용 표가 있다.
   - 아래에 문제마다 "정답은 ①이다 [1]."로 시작하는 답과 보기별 한 줄 설명이 있다.
   - 수동 채점 메모(p26-3, p50-2, p84-1)에 이유가 적혀 있다.
5. 직접 다시 돌려 보기(서버 필요, Gemini 약 15회 사용)
   - 서버 켜기: `cd backend; uv run uvicorn app.main:app --port 8000`. 모델 로딩에 약 1분 걸린다.
   - 다른 창에서 `cd backend; uv run python -m app.qa.mcq_run run`을 실행한다. 끝에 "자동 채점 맞음 13, 틀림 0, 검토 필요 2" 정도가 나오면 된다.
   - 비교: `uv run python -m app.qa.mcq_run compare 새결과.json 20261001-183237.json --baseline 20261001-171504.json`
6. 일반 질문이 그대로인지 확인: 서버를 켠 상태에서 `cd backend; uv run python -m app.qa.sample_run --ids a01,a06,b05,c01,c07,c06,c09,n08,n01,n07`을 실행한다. 답변 7개, 확인 불가 3개(n08·n01·n07)가 나오면 된다. 결과는 `data/reports/answers/`.
7. DataGrip: `mingyu.query_logs`의 최근 행에서 `metadata → citation_check → unsupported_option_sentences`를 보면 객관식 질문에서 "확인되지 않는다"고 쓴 보기 줄 수가 보인다.
